1. Introduction and learning objectives

Generating an executable image is the process of transforming a program written in a high-level language or assembly language into a machine-readable file that a processor can execute. In embedded systems, the resulting image must also fit the target device's memory layout and startup requirements.

Core idea: Source code is not normally executed directly by a microcontroller. It passes through translation and build stages; the linker combines code and data, resolves symbols, and places sections according to a memory layout. A tool may then convert the linked output into a programming image such as Intel HEX or Motorola S-record.
Why it matters

Correct build settings affect device compatibility, code size, startup, memory placement, debugging symbols, and reliable firmware deployment.

Prerequisites

C/assembly basics, compiler and assembler roles, CPU instruction set, RAM versus non-volatile memory, and basic file-system concepts.

Important terminology

TermMeaning
CompilerTranslates source code into assembly or target object code, depending on the toolchain.

2. Process overview: source to executable image

The exact tools vary by processor and IDE, but the logical flow is broadly consistent.

Important distinction: preprocessing, compilation, assembling, and linking are build stages. Flashing/programming and runtime testing are deployment and verification stages, even though they are often shown in the full firmware workflow.

3. Each stage explained

1

Write source code

Create C/C++ or assembly files and header files. Include startup code, peripheral drivers, application logic, and required libraries.

2

Preprocess

Expands #include and macros, and evaluates conditional compilation directives. The output is a translation unit prepared for compilation.

3

Compile

Checks language rules, performs optimization, and translates source into target assembly or object-level representation. Compiler options control CPU architecture, ABI, optimization, and debug information.

4

Assemble

Encodes assembly instructions into machine-code sections and emits an object file. Symbols may remain unresolved until linking.

5

Link

Combines object files and libraries, resolves references between modules, applies relocations, places sections, and checks memory-region constraints using a linker script or configuration.

6

Convert / package

Where required, converts the linked file into a programming format such as Intel HEX or S-record, or packages it with metadata, checksums, signatures, or a bootloader header.

7

Load or program

A debugger/loader can place an image in RAM, or a programmer writes the firmware to non-volatile memory such as flash. The method depends on the target and boot flow.

8

Verify and debug

Check build logs, map file, memory usage, image integrity, startup behaviour, peripheral operation, and runtime tests. Debug symbols help map machine instructions back to source.

Common outputs by stage

StagePossible artifactWhat to check

4. Memory layout and executable image formats

The linker places sections into memory regions defined by the target memory map. Typical embedded programs store instructions and constant data in flash/ROM while writable variables occupy RAM.

Startup detail: in many bare-metal systems, the initial values for .data are stored in flash but copied to RAM at startup. The .bss region is usually cleared to zero before the application reaches main(). This behaviour is implemented by startup/runtime code and is target-specific.
FormatTypical useKey note
ELF / executable outputLinking, debugging, loaders, symbol informationMay include symbols and debug sections not programmed into flash.
Intel HEXDevice programming over supported toolsText records carry data and addresses, with checksums.
Motorola S-recordFirmware transfer/programmingText records encode address/data and checksums.
Raw binary (.bin)Bootloaders or direct flash programmingUsually lacks intrinsic address and symbol metadata; tool must know where it belongs.

Key relationship

A successful build can be expressed as a conceptual condition:

Build success = translation succeeds + symbols resolve + sections fit target memory

This is a teaching summary, not a formal compiler equation. Some toolchains also enforce security, signing, checksum, or packaging rules.

5. Worked examples

Because this is a toolchain/process topic, the examples use realistic build decisions and memory accounting rather than unrelated circuit equations.

Example 1 — Find the missing build stage

Question: Compilation produces main.o and sensor.o, but the final command reports “undefined reference to read_sensor”. What should be checked first?

  1. Identify the stage: the message is from the linker.
  2. Check the symbol: confirm that a definition of read_sensor is compiled and included in the link command or library.
  3. Check spelling and linkage: compare function name, signature, C/C++ linkage, and conditional compilation.
  4. Conclusion: include the correct object/library or fix the symbol mismatch; recompiling unrelated files may not help.
Answer: Diagnose the link inputs and symbol definition. An undefined reference is generally a link-time problem, not a flash-programming problem.

Example 2 — Check flash capacity

Question: A target has 256 KiB of flash. The map report lists 184 KiB of code, 24 KiB of read-only constants, and 12 KiB of other flash-resident metadata. Does this fit, ignoring reserved bootloader space?

  1. Used flash = 184 + 24 + 12 = 220 KiB.
  2. Available flash = 256 KiB.
  3. Remaining = 256 − 220 = 36 KiB.
  4. Since 220 KiB is less than 256 KiB, it fits under the stated assumption.
Answer: 220 KiB used; 36 KiB remaining. If a bootloader or reserved region occupies flash, subtract that space before deciding.

Example 3 — GATE-style image-size calculation

Question: A firmware image contains 48,000 bytes of code, 6,000 bytes of constants, and 2,000 bytes of image metadata. What is the total payload size in decimal kilobytes (kB)?

  1. Total bytes = 48,000 + 6,000 + 2,000 = 56,000 bytes.
  2. Decimal conversion: 1 kB = 1,000 bytes.
  3. Size = 56,000 / 1,000 = 56 kB.
Answer: 56 kB. If a question uses KiB, divide by 1,024 instead; state which unit convention is used.

6. Simulation software: Multisim context

Multisim is primarily a circuit simulation environment for analog, digital, and mixed electronic circuits. The process of generating a processor executable image is normally performed by a compiler toolchain and target IDE, not by a circuit simulator itself.

Therefore this page shows an illustrative build pipeline and memory map, not measured Multisim results. For an embedded firmware lab, pair the circuit simulation (if supported by the chosen model) with the relevant MCU compiler, linker, and programming tools.

Suggested lab verification checklist

  • Build the project and inspect compiler warnings/errors.
  • Confirm that the selected target MCU and instruction set match the hardware.
  • Inspect the linker map for flash/RAM use and section addresses.
  • Generate the format required by the programmer or bootloader.
  • Program the correct device and verify the written image.
  • Run a simple startup/peripheral test and preserve build logs for reproducibility.

7. GATE-style practice questions

These are original practice questions, not claimed previous-year GATE questions. Select an answer and expand the explanation.

Easy Q1. Which tool normally resolves external symbols across object files?
Answer: Linker. The linker combines object files/libraries, resolves references, applies relocations, and places sections. The compiler translates source; the programmer writes the image to the device.
Easy Q2. Which artifact commonly contains relocation information and unresolved external symbols?
Answer: Object file. A relocatable object file can contain code/data sections and symbol/relocation tables. It is not necessarily a final executable image.
Moderate Q3. A 512 KiB flash has 320 KiB code, 72 KiB constants, and 24 KiB metadata. How much remains?
Answer: 96 KiB. Used = 320 + 72 + 24 = 416 KiB. Remaining = 512 − 416 = 96 KiB, assuming no other reserved regions.
Moderate Q4. What is the primary purpose of a linker script in many embedded toolchains?
Answer: Define memory regions and control placement of sections/symbols. Exact syntax and capabilities depend on the linker.
Easy Q5. Which stage expands C preprocessor macros and includes?
Answer: Preprocessing. It handles directives such as #include, #define, and conditional compilation.
Moderate Q6. Why might a .bin file need an externally specified start address?
Answer: A raw binary typically stores bytes without the address records or symbol metadata found in formats such as Intel HEX or ELF. The programmer/bootloader must know where to place it.
Difficult Q7. A linker reports that the .bss section overflows RAM. Which fix is most directly relevant?
Answer: Reduce RAM usage or correct the memory layout after checking the map file. Changing the flash HEX conversion alone will not fix a RAM section overflow.
Moderate Q8. In a common bare-metal startup sequence, what happens to .data and .bss?
Answer: Initialized .data values are copied from their load image (often in flash) to RAM, and .bss is cleared to zero before application code runs. Details are runtime/target-dependent.
Difficult Q9. A source file compiles, but a function is missing at link time. Which check is most useful?
Answer: Check whether the object/library defining the function is linked, and inspect symbol spelling, linkage, and conditional compilation.
Moderate Q10. Which file is especially useful for investigating where code and data were placed?
Answer: Linker map file. It commonly reports section addresses, symbol placement, and memory consumption.

Quick GATE strategy

  • Map the error to its stage: syntax/type error → compile; undefined reference/duplicate symbol → link; wrong address/content on device → image/programming/boot stage.
  • For memory questions, add only the sections specified and subtract from the stated capacity.
  • Do not assume every toolchain emits every intermediate file or uses the same file extensions.

8. Core electronics / embedded interview questions

Open each question to review a concise interview-ready answer.

1. Explain the process of generating an executable image.
Source files are preprocessed, compiled, assembled into object files, then linked with required objects/libraries. The linked output may be converted to HEX/S-record/BIN, programmed into target memory, and verified through tests/debugging.
2. What is the difference between a compiler and a linker?
A compiler translates an individual source translation unit and checks language-level rules. A linker combines object files/libraries, resolves cross-module symbols, applies relocations, and places sections.
3. Why does an embedded project need a linker script?
It tells the linker how sections map to target memory regions, such as flash and RAM, and can define addresses for vectors, code, data, stack, and reserved regions.
4. What is the difference between ELF and Intel HEX?
ELF is a structured executable/object format that can contain program sections, symbols, and debug information. Intel HEX is a text-based record format commonly used to transfer addressed bytes to programming tools.
5. How do you investigate an undefined reference error?
Find the missing symbol; confirm its definition exists, its source was compiled, the corresponding object/library is linked, and the name/linkage matches. Inspect build commands and symbol tables if necessary.
6. How can you reduce firmware image size?
Use appropriate optimization, remove unused code/data through supported dead-code elimination, avoid unnecessary libraries, select compact data types where correct, and inspect the map file. Verify timing and behaviour after optimization.
7. What do .text, .data, .bss, and .rodata usually represent?
.text: instructions; .data: initialized writable data; .bss: zero-initialized/uninitialized static storage; .rodata: read-only constants. Exact section naming and placement vary by toolchain.
8. The image builds but the MCU does not start. What would you check?
Verify target/clock and boot configuration, reset and vector table placement, entry point/startup code, flash address, programmer verification, watchdog/security settings, and debug the reset path. Use the map file and debugger rather than assuming the compiler is at fault.
9. What is a map file and why is it useful in validation?
It reports linked sections and symbols with addresses and sizes. Engineers use it to check flash/RAM limits, locate unexpected library growth, and confirm critical sections are placed correctly.
10. What is a reproducible firmware build?
A build whose output can be recreated from controlled source, toolchain versions, build options, dependencies, and configuration. Teams preserve versioned scripts, compiler versions, logs, and artifact hashes.
11. What changes when building for a different MCU?
Target ISA/ABI, startup code, linker memory map, device headers, peripheral drivers, compiler flags, libraries, and programming configuration may all need to change.
12. How is a simulation workflow different from image generation?
Circuit simulation evaluates a modelled circuit's electrical behaviour. Executable-image generation translates and links firmware for a processor. They can support the same project but are different processes and tools.

Industry perspective

Firmware teams automate the build in CI, enforce compiler warnings, inspect memory reports, sign or checksum release images where required, archive versioned artifacts, and program/test representative hardware. A reproducible, traceable image is important for field updates, safety reviews, and debugging deployed products.

10. Quick revision sheet

Advantages and limitations

Advantages
  • Separates development into testable stages.
  • Supports modular code and reusable libraries.
  • Enables optimization, memory accounting, and debugging.
  • Build automation improves repeatability.
Challenges
  • Target-specific settings and linker scripts can be error-prone.
  • Library/configuration mismatches can cause link failures.
  • Flash/RAM limits may constrain features.
  • Wrong image format/address or boot configuration can prevent startup.

Common misconceptions

  • “Object file = final executable.” Not necessarily; it may be relocatable and have unresolved symbols.
  • “HEX conversion fixes all build problems.” It does not fix compile/link errors or incorrect memory layout.
  • “A successful build guarantees working hardware.” Hardware, startup, clocks, pin configuration, and peripherals still need validation.
  • “Multisim generates every MCU firmware image.” The executable is generally generated by the target's compiler/linker toolchain.
Exam-ready answer: An executable image is generated by preprocessing source files, compiling them into target code, assembling object files, and linking the required modules and libraries. The linker resolves external symbols and places program sections according to the target memory map. The output may be converted into HEX, S-record, or binary format, programmed into the target, and verified through debugging and testing.
